# S1-3 · manifest——每批数据的"施工总结"（也是户口本）

## 你在哪（路线图）

- ✅ 0-0 全景导览
- ✅ S1-1 发一条生成命令
- ✅ S1-2 配方文件与表结构
- ⬜ **S1-3 manifest 生成记录：它记了什么、为什么每个数字都能溯源到它 ← 你在这**
- ⬜ S1-4 质量闸门

## 三问

**这一步干嘛？**
把 S1-1 返回时你一眼扫过的那个 `manifest`（当时写着 `{ ... }` 直接跳过了）完整读一遍——就 5 段内容，读完你会发现它把"这批数据是谁、几点、用什么造的"全交代了。

**为什么必须有它？**
想象半年后有人指着一张报表问你："这 31,390 行产量数据哪来的？用什么参数造的？检查过没有？"——答不上来，这批数据就是**黑数据**，谁也不敢用。manifest 就是让这三个问题永远有答案的回执。

**这一步解决什么麻烦？**
解决"说不清来历"。学完这课你能做到：给任何一个 run_id，一分钟内查出它的配方、种子、行数、检查结果——不用翻代码，不用问人。

## 一份真实的 manifest，分 5 段读

还是用 S1-1 那次的 run（`tpa_s1_demo-20260928-004903-0aaedb`），下面全是真实内容。

**第 1 段：身份段——谁、几点、什么环境造的**

```json
"tool": "fieldforge",
"version": "0.1.0",
"python": "3.12.14",
"generated_at": "2026-09-28T00:49:18+00:00"
```

时间是 UTC（世界标准时间），比北京时间慢 8 小时——你早上 8 点 49 跑的，它记 00:49，别以为自己眼花。连 Python 版本都记，是有讲究的（闯关题 3 等你）。

**第 2 段：参数段——用什么图纸、施工单、种子**

```json
"schema": { "name": "tpa-contract", "version": "0.1.0", "file": "/app/schemas/tpa-contract-v0.1.yaml" },
"recipe": { "name": "tpa_s1_demo", "seed": 20260927, "period": { "start": "2025-09-01", "days": 365 }, ... },
"seed": 20260927,
"output_format": "csv"
```

注意 **seed 出现了两次**：`recipe.seed` 是配方里写的默认值，最外层（不在 recipe 缩进里面的那个）`seed` 是这次**实际生效**的值。平时两处一样；如果发命令时用 `"seed": 7` 覆盖了默认值，两处就不同——一眼就能看出"这批数据没用默认种子"。

**第 3 段：产出段——出了哪些文件、各多少行、什么单位**

```json
"entities": [
  { "entity": "well_info", "file": "well_info.csv", "rows": 120 },
  { "entity": "oil_production_daily", "file": "oil_production_daily.csv", "rows": 31390 },
  ... 共 14 条
],
"units": { "oil_production_daily": { "oil_output": "t", "water_cut": "%", "oil_pressure": "MPa", ... }, ... }
```

眼熟吧：**S1-1 你看的那张"14 张表行数"清单，就是照这段念的**；S1-1 说"单位来自 manifest 不是猜的"，出处就是 `units` 这段。（well_info 的单位是空的，因为它 9 列全是文字，没有带单位的数值列。）

**第 4 段：体检段——数据查过了没有**

```json
"conformance": { "status": "pass", "checked_cells": 4603081 },
"injection": { "enabled": false },
"gate": { "overall": "pass", "summary": { "pass": 19, "warn": 0, "fail": 0, "skipped": 6 }, "enforce": true }
```

三句话读完：
- conformance：数据按图纸（合同）逐格检查过，查了 4,603,081 个格子，全合格；
- injection：没注脏数据——这是干净版本，`tpa_s1_dirty` 配方这里会是 `true`（S2 讲）；
- gate：19 条质量规则通过、6 条这次没启用，闸门是强制模式——数据没过闸门就不许出库使用（S1-4 细讲）。

**第 5 段：声明段——我是假的**

```json
"synthetic_data_declaration": "本数据集由 fieldforge 生成的合成数据：仅可用于算法研发、测试、演示与教学；禁止用于储量申报、生产决策等任何真实业务场景。"
```

跟 S1-1 你在响应头里看到的英文声明是同一件事的中文版，一个写在文件里，一个写在下载口上。

## manifest 的闭环：数据可以丢，种子不能丢

把三课连起来看：配方和合同定"怎么造"（S1-2），种子定"抽中哪支签"（S1-1 实验 3），manifest 把这两样连同造出来的结果一起存档（本课）。所以：

> 只要在同一套环境（同一台服务器、同一个工具版本）里，抄下 manifest 里的**配方名 + seed**，任何时候重发一次命令，就能一字不差地把整批数据再造出来。（真的只要这两样吗？想搬到别的机器呢？闯关题 1 等你。）

数据会丢、硬盘会坏，但"配方名+种子"只有十几个字，抄在纸上也行。这就是"每个数字都能说清来历"的底气。

## 亲手验证清单

1. 把自己那次运行的 manifest 存下来看全貌（`<你的run_id>` 换成你 S1-1 记下的那串，形如 `tpa_s1_demo-20260928-004903-0aaedb`；`-o` 是"把结果存成这个文件名"，S1-1 用过）：

```bash
curl http://8.163.33.135/api/runs/<你的run_id>/download/manifest.json -o manifest.json
```

2. 或者直接看、不存成文件（注意这两个网址长得不一样：带 `/download/` 的是下载文件接口，不带的是查询接口直接吐内容，效果一样）：

```bash
curl http://8.163.33.135/api/runs/<你的run_id>/manifest
```

3. 在 manifest 里找出三个信息，答这三问：这批数据的种子是多少？油压（oil_pressure）的单位是什么？闸门过了没有？
4. 看"历史运行列表"（它是 manifest 的摘要版，一次看全部）：

```bash
curl http://8.163.33.135/api/runs -o runs.json
```

每个 run 一条记录：run_id、配方、种子、各表行数、闸门结果。注意一个现象：`tpa_s1_demo` 这一族（同配方跑出来的那些次）gate 是 `pass`，`one_well_365d` 这一族是 `not-run`——那个配方压根没写 gate 配置，没开闸门，manifest 如实记"没跑"。
5. 回看 S1-1 第 2 步的返回——`"manifest": { ... }` 那一段，就是本课这份文件。其实你早就见过它了。

## 捣乱实验

**实验 1：查一个不存在的 run 的户口。**（`-i` 是"连状态码一起显示"，S1-1 教过）

```bash
curl -i http://8.163.33.135/api/runs/bu_cun_zai_de_run/manifest
```

实测：HTTP 404，`{"detail": "run 不存在：bu_cun_zai_de_run"}`。查无此户，如实报错。

**实验 2：对比两份 manifest，看哪些相同、哪些不同。**
拿你手头两个不同配方的 run（比如 tpa_s1_demo 和 one_well_365d），各下 manifest 对照：
- 不同：run_id、generated_at、schema 名（tpa-contract 对 fieldforge-core）、表清单、gate（pass 对 not-run）；
- 相同：tool 都是 fieldforge——**manifest 是每批数据各有一份的"户口本"，不是全系统共用一张表**。

## 闯关题（先自己答，答案在最底下）

1. 服务器硬盘坏了，这批数据全没了。要在别的机器上一字不差地重造，至少要从 manifest 抄下哪几样？为什么光把 CSV 文件备份走不算完？
2. seed 在 manifest 里出现两次（`recipe.seed` 和顶层 `seed`）。哪个是实际生效的？这个"写两处"的设计什么时候派上用场？
3. 为什么 manifest 连 Python 版本都记下来？

---
---

**闯关答案（做完题再看）**

1. 分两种情况。**还在原来那套环境**（同一台服务器、同一个工具版本）：抄两样就够——配方名 + seed。**要搬到别的机器重造**：得抄四样——配方名（连配方文件内容）、schema 名和版本、seed、tool/Python 版本，因为不同 Python 版本的随机序列可能不同（见第 3 题）。为什么光把 CSV 文件备份走不算完——CSV 只有结果，没有"它是按什么参数造的"这段来历；下次想扩样（多造几天、换个井数）就抓瞎了。备份数据，更要备份"数据的设计图"。
2. 顶层 `seed` 是实际生效的。发命令时可以用 `"seed": 7` 覆盖配方默认值，这时 `recipe.seed` 还是 20260927、顶层变成 7——两处一比，就知道"这批数据没用默认种子"，排查"为什么两批数据不一样"时第一眼看这里。
3. 因为"同种子同输出"只在**同一个 Python 版本里**成立：随机数算法在 Python 不同版本间不保证一致，换了版本可能重造出不一样的数据（引擎源码 `engine.py` 开头注释就写了这条）。manifest 记下版本，将来复现对不上时，先查版本就知道是不是这个原因。
