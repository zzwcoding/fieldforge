## 三问

**这一步干嘛？**
打开两个本地文件——配方 `recipes/tpa_s1_demo.yaml` 和表结构 `schemas/tpa-contract-v0.1.yaml`——看懂"生成什么"是写在哪的，并把 S1-1 下载的 CSV 列名跟合同逐列对上。

**为什么分成两个文件？**
分工不同：
- **配方（recipe）**：这一次施工的**施工单**——什么时间范围、几个种子、输出什么格式。管"这一次怎么干"。
- **合同（schema，数据合同）**：整套**图纸+工艺卡**——一共哪些表、每张表哪些列、每列什么类型和取值范围、每张表按什么规律造数。管"东西长什么样"。

分开的好处：换一次施工只要换施工单（配方全文只有 20 行）；表结构稳定，不用每次重写。

**这一步解决什么麻烦？**
上一课你看到 14 张表"凭空"冒出来。这一步让你能指着文件回答："第 7 张表的第 3 列为什么叫这个名字"——所有规定都落在你本地这两个文件里，一个不多。

## 再看合同（真正的大头）

打开 `/Users/divh/Downloads/fieldforge/schemas/tpa-contract-v0.1.yaml`，全文 480 行，骨架只有一套：

```
entities:            ← 大清单：全部 14 张表都列在这下面（S1-1 的 14 张表就是这 14 段，你可以自己数）
  well_info:         ← 一张表一段
    fields:          ← 这张表有哪些列
      well_id: …
  oil_production_daily:
    …
```

其余 470 行都是往这套骨架里填内容。挑两张表看懂读法，剩下的你照着读就行。

**第一张：well_info（井档案），9 列**。每列几件事：类型、取值范围、生成器、说明。两个例子先看懂：

```yaml
well_type:
  type: enum            # 枚举 = 只能取列出的几个值
  values: [EW, IW]      # 只许是采油井或注水井
block_name:
  type: enum
  values: [渤南, 渤中, 渤西]   # 你 S1-1 看到的三个区块，源头在这行
```

再看一个"四件事"齐全的列（井筒表的井深，拿它认全各种写法）：

```yaml
measured_depth:
  type: float              # ① 类型：小数
  unit: m                  #    单位：米
  range: [1500, 4800]      # ② 取值范围：在 1500~4800 之间抽
  generator: float_range   # ③ 生成器：告诉引擎"按范围随机抽数"这个动作
  description: 测量井深     # ④ 说明：给人看的注释
```

开头还有一段"这张表怎么造"的参数：

```yaml
model: master_wells          # 用引擎里哪个"造数模型"
model_params:
  count_ew: 86               # 86 口采油井
  count_iw: 34               # 34 口注水井   ← 120 口井的出处就是这两行
  status_weights: [0.92, 0.04, 0.03, 0.01]   # 现状抽签的概率比例：92% 生产中、4% 停产、3% 检修、1% 待弃置
```

对个账：S1-1 实测现状是生产中 109、停产 6、检修 4、待弃置 1。按 92:4:3:1 的比例抽 120 次，大概会抽出 110/5/4/1——实测 109/6/4/1，抽签有波动，对得上。

**第二张：oil_production_daily（采油日报），核心表**。它的开头有一串"数字按什么规律生成"的参数：

```yaml
model: tpa_daily_production
model_params:
  initial_oil_rate_t_per_d: [15, 50]   # 井的初始日产油：15~50 吨里抽
  arps_b: [0.4, 0.9]                   # 递减曲线形状（S3 讲 Arps 递减）
  water_cut_start: [0.05, 0.20]        # 含水率从 5%~20% 起步
  water_cut_end: [0.50, 0.75]          # 一年后爬到 50%~75%
  downtime_prob_per_day: 0.02          # 每天有 2% 概率停机
```

回想 S1-1 你看的 Z-01：第一天含水 16.25%——正好落在起步区间 5%~20% 里。**你看到的数据，就是这些参数算出来的**：参数在合同里，数据在 CSV 里，两头能对上。

## 引擎怎么消费这两个文件（代码证据）

引擎就一个循环（`fieldforge/engine.py:50-53`）：

```python
def generate(self):
    for name, ent in self.schema.entities.items():   # 按合同声明顺序，一张表一张表来
        self.tables[name] = self._gen_static(...) if ent.model is None else self._gen_model(...)
```

两种造法：
- 表开头写了 `model: 某名字` → 引擎按名字调对应的函数。对照表在 `engine.py:116-124`：合同写 `tpa_daily_production`，引擎里就有 `_model_tpa_daily_production()`（`engine.py:222`），产量怎么递减、含水怎么爬全在这个函数里；
- 没写 model 的表 → 按列定义逐格造：枚举列在 values 里抽、范围列在 range 里抽。

所以"**改表不用改代码**"这句话现在可以拆成两句实话：
- **改参数不改代码**：井数改成 200、天数改成 730、含水起点改区间——都只动合同/配方文件，引擎一行不动；
- **换生成规律要写新函数**：想让产量按全新的物理规律走，合同里可以指一个新 model 名，但引擎里得有这个函数（这是 S3 物理模拟器升级通道的事）。

## 收 S1-1 欠的两笔行数账

上一课有两张表没对账，账本就在合同里：

**sensor_reading_subdaily（210,240 行）**——重点井的高频读数：

```yaml
model_params:
  wells_limit: 2            # 只挑 2 口重点井
  interval_minutes: 15      # 15 分钟记一次 = 一天 96 条
```

乘法：2 口井 × 3 个通道 × 96 条/天 × 365 天 = **210,240** ✓。S1-1 留的疑问在这解开：210,240 ÷ 131,400 = 1.6，一张"一天多条"的表为什么只比日度表多六成？因为高频记录只有 2 口重点井在记，不是 120 口井全记。

**well_log_curve（288,120 行）**——测井曲线：

```yaml
model_params:
  depth_start_m: 1400
  depth_end_m: 2600
  step_m: 0.5               # 每半米一行
```

乘法：(2600 − 1400) ÷ 0.5 + 1 = 2,401 行/井，× 120 口井 = **288,120** ✓（+1 是因为起点 1400 米那一行也算一条）。

**还有一类"抽签账"**：检泵 19 条、措施 59 条、化验 987 条——这些按概率抽签生成（比如每口井每天 2% 概率出一次事件），同一次生成里抽中哪些就是哪些；只要种子不变，重跑抽出来的结果一模一样，但不该用乘法硬算。以后看到"对不上乘法的行数"，先想抽签。

**闯关答案（做完题再看）**

**捣乱实验 2 的答案**：动合同文件 `schemas/tpa-contract-v0.1.yaml` 里 well_info 的 `count_ew: 86` 和 `count_iw: 34` 这两行（比如改成 130 和 70，合起来 200），引擎代码一行不动，重新生成就是 200 口井的版本。井数一变，日报行数会自动跟着变（日报 = 采油井数 × 天数），因为那也是乘出来的。

1. 配方=这一次施工的施工单（时间范围、种子、格式、用哪套合同）；合同=图纸+工艺卡（哪些表、哪些列、每列取值范围、按什么规律造数）。
2. 2 口重点井 × 3 通道 × 96 条/天（15 分钟一条）× 365 天 = 210,240。四个数全部来自合同：`wells_limit: 2`、每井 3 通道（sensor_channel 表）、`interval_minutes: 15`、配方 `days: 365`。
3. 说明这批数据真是按合同参数生成的：Z-01 起步含水 16.25% 落在合同规定的起步区间 5%~20% 内。**参数在合同、数据在 CSV，两头能对账**——这就是"合成但讲道理"的意思，也是下一课 manifest 要把参数记下来的原因。
