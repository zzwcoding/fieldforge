# S1-1 · 亲手发一条生成命令，看 67 万行数据怎么出来

## 你在哪（路线图）

终极目标：学懂 fieldforge——合成数据怎么造出来、怎么被检查、怎么被查询、怎么对外服务。

当前场景 S1「一条合成数据的出生」，共 4 步：

- ✅ 0-0 全景导览：知道系统里有哪 5 个程序、一条数据经过哪 5 步
- ⬜ **S1-1 亲手发一条生成命令，看 67 万行数据怎么出来 ← 你在这**
- ⬜ S1-2 配方文件：14 张表、每张表有哪些列，是谁规定的
- ⬜ S1-3 manifest 生成记录：每次生成自动留下的"施工总结"
- ⬜ S1-4 质量闸门：数据检查不过，为什么出不了库

## 三问

**这一步干嘛？**
你自己在终端发一条命令给云服务器，等十几到二十几秒，拿到 14 个数据文件、67 万多行数据，再打开文件看看里面长什么样。

**为什么用程序生成，不手工造数据？**
三个原因：
1. 量太大。67 万行，手工造不现实；
2. 要能重来。做测试经常需要"跟上次一模一样的数据"，程序做到这一点靠"随机种子"（下面解释）；
3. 要声明是假数据。假数据混进真业务会出事故，所以每个数据文件都带"我是合成的"声明。

**这一步解决什么麻烦？**
解决"我第一次接触这个系统，怎么确认它真的能干活"。你亲手发一条命令，亲眼看到数据落地，后面的课程全部建立在这个动作上。

## 发命令前，先认识 5 个词

| 词 | 大白话解释 |
|---|---|
| curl | 一个命令行小工具，替你给服务器发请求。Mac 和 Linux 自带，直接用 |
| GET / POST | 请求的两种常用类型。GET 是"我要看东西"，POST 是"我提交一个任务让你干" |
| JSON | 一种"键: 值"成对写的文本格式，程序之间传数据常用 |
| HTTP 状态码 | 服务器回复时带的三位数字：200=成功，404=你要的东西不存在，429=正忙、先别发，403=这个不给拿 |
| `curl -i` | curl 加上 `-i` 这个选项，会把状态码和回复头一起打出来，看得见服务器到底回了个啥 |

还有两个本项目专属的词：

- **配方（recipe）**：一份施工设计书，写清楚这次生成要什么——多少口井、多少天、哪些表。配方是 yaml 文件（一种缩进式配置文件格式，`键: 值` 一行一条）。
- **随机种子（seed）**：随机数不是凭空变的，它像"洗牌的起手顺序"——起手顺序一样，洗出来的牌序就一样。本配方种子是 20260927，同一种子每次生成的数据**一字不差**（下面实验 3 会当场验证）。

## 第 1 步：看看服务器上有哪些配方

打开 Mac 终端，复制粘贴这条命令（`#` 开头是注释，不用粘贴）：

```bash
curl http://8.163.33.135/api/recipes
```

这条没写 `-X`，不加 `-X` 就是 GET（看东西），不用提交任务。

实测返回（整理过换行）：

```
{"recipes": [
  {"name": "one_well_365d",         "description": "一口井 × 365 天（well / wellbore / sensor_channel / production_daily 四表）"},
  {"name": "one_well_365d_injected","description": "一口井 × 365 天，注入坏点/缺测/连续停机"},
  {"name": "one_well_365d_sensors", "description": "一口井 × 365 天五表（含 sensor_reading）"},
  {"name": "tpa_s1_demo",           "description": "tpa 数据合同 8 表 + 井筒/传感器辅助实体 · 120 井 × 365 天"},
  {"name": "tpa_s1_dirty",          "description": "120 井 × 365 天 · A/B 班重复 / 配产双值 / 单位误录 / 旧井号 …"}
]}
```

共 5 个配方。今天用 `tpa_s1_demo`（干净基线：造出来的是"好数据"）。两处字面先解释一下，省得你卡住：**tpa** 是本数据要服务的平台的名字（Petro-Agent 的缩写，教学项目里的假想油田智能平台）；**"数据合同"** 就是"表结构的规定"——一共哪些表、每列叫什么、什么单位，S1-2 整课讲它。带坏数据的 `tpa_s1_dirty` 是 S2 的教材，先不碰。

## 第 2 步：发生成命令

```bash
curl -X POST http://8.163.33.135/api/generate \
     -H "Content-Type: application/json" \
     -d '{"recipe": "tpa_s1_demo"}'
```

这条命令拆开看：
- `-X POST`：提交任务；
- `-H "Content-Type: application/json"`：告诉服务器"我发的内容是 JSON 格式"；
- `-d '{"recipe": "tpa_s1_demo"}'`：任务内容——用 tpa_s1_demo 这份配方。想换种子加 `"seed": 7`；想换文件格式加 `"format": "parquet"`（parquet 是另一种数据文件，分析工具读它更快；不写就是 CSV，本课用 CSV 就够）。

实测等了 20.7 秒（另一次实测 11 秒，快慢看服务器当时忙不忙），返回：

```json
{"run_id": "tpa_s1_demo-20260928-004903-0aaedb",
 "manifest": { ... }}
```

- **run_id**（本次运行编号）= 配方名 - 日期时间 - 6 位随机码。以后凡是要"指哪一次生成"，都用它。
- **manifest**（生成记录）= 干完活自动写的"施工总结"。里面最要紧的是 14 张表各生成多少行：

| 表 | 行数 | 是什么 |
|---|---:|---|
| well_info | 120 | 井档案：井号、类型、平台、区块、现状 |
| wellbore | 120 | 井筒：每口井的深度结构 |
| sensor_channel | 360 | 传感器通道：每口井 3 个（井口压力、管线温度、含水率） |
| equip_status | 86 | 采油设备现状（86 口采油井各一行） |
| oil_production_daily | 31,390 | 采油井每天的生产记录 |
| water_injection_daily | 12,410 | 注水井每天的注水记录 |
| well_overhaul | 19 | 检泵修井记录（把井下泵提上来检修这类作业） |
| well_measures | 59 | 增产措施记录（压裂、酸化等） |
| fluid_test | 987 | 流体化验记录（含水、密度） |
| monthly_settlement | 36 | 月度结算：3 个区块 × 12 个月 |
| injection_connection | 65 | 注采对应：哪口注水井给哪口采油井供水 |
| sensor_reading | 131,400 | 传感器读数（每通道每天一条） |
| sensor_reading_subdaily | 210,240 | 传感器读数（一天多条） |
| well_log_curve | 288,120 | 测井曲线（仪器下井测岩石性质，每半米一行） |

**合计 675,412 行，约 67.5 万。**

这些行数不是拍脑袋编的，挑 5 张对账给你看：
- 采油日报 31,390 = 86 口采油井 × 365 天；
- 注水日报 12,410 = 34 口注水井 × 365 天（86 + 34 = 120 口，对上井档案）；
- 传感器读数 131,400 = 360 个通道 × 365 天（120 井 × 3 通道）；
- 月度结算 36 = 3 个区块 × 12 个月（哪 3 个区块？well_info 里 block_name 一列只有三个值：渤南、渤中、渤西，各 44、45、31 口井）；
- 日期从 2025-09-01 起第 365 天，正好到 2026-08-31。

剩下两张传感器大表的行数怎么定的（一天记几条、井深多深记一行）由配方里更细的规则决定，S1-2 讲。

manifest 还记着两件事（细节 S1-3、S1-4 讲）：
- 质量闸门结果：19 条规则通过、0 条不通过、6 条这次没启用——闸门不通过数据就不出库；
- 合成声明原文："本数据集由 fieldforge 生成的合成数据：仅可用于算法研发、测试、演示与教学；禁止用于储量申报、生产决策等任何真实业务场景。"

## 第 3 步：把数据下载下来，亲眼看两眼

下载地址格式：`http://8.163.33.135/api/runs/<run_id>/download/<文件名>`。
下面示例命令里写的是**作者那次的 run_id**——你原样粘贴也能下载（同种子的数据一样），想下自己那次生成的，就把 run_id 换成你第 2 步拿到的那串。

```bash
# 下载井档案和采油日报（-o 后面跟名字 = 把下载的文件存成这个名字）
curl http://8.163.33.135/api/runs/tpa_s1_demo-20260928-004903-0aaedb/download/well_info.csv -o well_info.csv
curl http://8.163.33.135/api/runs/tpa_s1_demo-20260928-004903-0aaedb/download/oil_production_daily.csv -o oil_production_daily.csv

# 各看几行（CSV：一行一条记录，字段用英文逗号隔开。
#   Mac 的 Excel 直接开 CSV 中文可能乱码，用 Numbers / WPS / 文本编辑器看更稳；
#   grep 是"按内容挑行"的小工具，下面用它把 Z-01 井的行挑出来）
head -3 well_info.csv
grep Z-01 well_info.csv
grep "^Z-01," oil_production_daily.csv | head -3
```

实测输出（head 的两行带表头；grep 只挑匹配行、不带表头，列的含义对照 head 那段表头看）：

```
well_id,well_name,well_type,first_prod_date,platform,block_name,field_name,current_status
N-01,渤南01,EW,2020-05-13,CEP-C,渤南,渤南油田,待弃置,
N-02,渤南02,EW,2019-03-21,CEP-D,渤南,渤南油田,生产中,

Z-01,渤中01,EW,2020-11-28,CEP-A,渤中,渤中油田,生产中,

well_id,prod_date,oil_output,liquid_output,water_cut,plan_output,open_days,oil_pressure,report_shift
Z-01,2025-09-01,16.65,22.34,16.25,17.04,24.0,7.03,B
Z-01,2025-09-02,15.95,21.43,16.35,17.04,24.0,7.45,B
Z-01,2025-09-03,15.97,21.48,16.45,17.04,24.0,7.16,B
```

看懂这几行的意思：
- 井档案：EW=采油井（注水井标 IW）。Z-01 是 2020 年 11 月投产的采油井，在 CEP-A 平台、渤中区块。120 口井的现状不是整整齐齐的：生产中 109 口、停产 6 口、检修 4 口、待弃置 1 口（待弃置 = 快到使用年限，准备封井退出）——真油田就是这样有生有停。
- 日报逐列解释（单位来自 manifest，不是猜的）：
  - oil_output 日产油 16.65 吨；liquid_output 日产液 22.34 方（立方米）；
  - water_cut 含水率 16.25%（采出的液体里水占的比例）；
  - plan_output 配产 17.04 吨（上级定的"这天应该产多少"，实际围着它波动）；
  - open_days 24.0 = 这天开井生产了 24 小时；
  - oil_pressure 井口压力 7.03 MPa（兆帕，压力单位）；
  - report_shift B 班（采油工倒班，A/B 两班轮着录数）。

顺便验证一个"数字互相咬合"：22.34 方 × (1 − 16.25%) = 18.71 方油；再乘原油密度 0.89 吨/方 ≈ 16.65 吨——正好等于 oil_output。**液量、含水、油量三个数互相咬得上，这是数据"像真的"的第一层。** 0.89 这个密度不是我编的：Z-01 在 fluid_test 化验表里有 11 次化验记录，密度在 0.886~0.899 之间、平均 0.889，约等于 0.89（全库 987 次化验的密度在 0.85~0.92 之间）。这套咬合怎么造出来的，S3 整课讲。

最后看一个不起眼但重要的东西——服务器的回复头（回复时附带的一组说明信息）：

```bash
curl -D - -o /dev/null http://8.163.33.135/api/runs/tpa_s1_demo-20260928-004903-0aaedb/download/well_info.csv
```

选项拆开：`-D -` = 把回复头打到屏幕（那个 `-` 表示"打到屏幕"）；`-o /dev/null` = 文件内容别存（`/dev/null` 是系统的"垃圾桶"，写进去的东西直接扔掉）。合起来：只看回复头，不下载文件。

回复头里有一行（实测）：

```
x-synthetic-data: all outputs are synthetic; not for reserve filing or real business decisions
（所有产出都是合成数据；不得用于储量申报或真实业务决策）
```

每个下载都自带"这是合成数据"的声明，想删都删不掉——这是防误用的最后一道保险。

## 捣乱实验（故意搞错，看系统怎么接）

**实验 1：配方名写错。**
```bash
curl -i -X POST http://8.163.33.135/api/generate \
     -H "Content-Type: application/json" \
     -d '{"recipe": "bu_cun_zai_de_pei_fang"}'
```
实测：开头一行 `HTTP/1.1 404 Not Found`，正文 `{"detail": "配方不存在：bu_cun_zai_de_pei_fang"}`。报错说人话，不糊弄。

**实验 2：上一条还在跑，马上再发一条。**
先按 `Command+T` 再开一个终端标签页（一个窗口被占用时，命令在另一个窗口发），趁第一条还没跑完（有快有慢，11~21 秒；手太慢、第一条已经跑完了，就重发一条再试），在新窗口粘贴：

```bash
curl -i -X POST http://8.163.33.135/api/generate \
     -H "Content-Type: application/json" \
     -d '{"recipe": "tpa_s1_demo"}'
```
实测：`HTTP/1.1 429`，正文 `{"detail": "已有生成任务在跑（限流：同一时刻一个）"}`。
为什么限流：服务器只有 4 核 CPU、8G 内存，一次生成就要吃掉大半，同时跑两个会把服务器压垮。限流 = 故意规定"同一时刻只干一件事"。

**实验 3：种子决定一切。**
一共生成 3 次、下载 3 份、算 3 个指纹。先把 3 次的 run_id 抄在纸上备查。

```bash
# 第 1 次：默认种子 —— 你第 2 步已经跑过了，run_id 记为「甲」
# 第 2 次：还是默认种子，再跑一遍
curl -X POST http://8.163.33.135/api/generate -H "Content-Type: application/json" \
     -d '{"recipe": "tpa_s1_demo"}'        # run_id 记为「乙」
# 第 3 次：换种子 7
curl -X POST http://8.163.33.135/api/generate -H "Content-Type: application/json" \
     -d '{"recipe": "tpa_s1_demo", "seed": 7}'   # run_id 记为「丙」

# 下载 3 份井档案，各存一个名字（把 甲/乙/丙 换成你抄下的三个 run_id）
curl http://8.163.33.135/api/runs/甲/download/well_info.csv -o well_info_甲.csv
curl http://8.163.33.135/api/runs/乙/download/well_info.csv -o well_info_乙.csv
curl http://8.163.33.135/api/runs/丙/download/well_info.csv -o well_info_丙.csv

# 算文件指纹（md5 = 文件指纹：两份文件只要有一个字节不同，指纹就完全不同）
md5 well_info_甲.csv well_info_乙.csv well_info_丙.csv
```
实测（作者的甲乙丙）：
- 甲、乙（同为默认种子 20260927）：指纹都是 `5251f37e5048254f6f0f55cf9331280f`——**一字不差**；
- 丙（种子 7）：`bcd8769db970dc3c37db79e2287a2a5c`——**完全不同**。
结论：种子一样 → 数据一字不差；种子一换 → 数据整个变。这就是"可重来"的底气。

**实验 4：下载不在允许名单里的文件。**
```bash
curl -i "http://8.163.33.135/api/runs/<你的run_id>/download/secret.csv"
```
实测：`HTTP/1.1 403`，正文 `文件不在白名单：secret.csv（可下载：[...16 个文件名...]）`。
白名单 = 允许名单，名单上 16 个文件（14 张表 + manifest.json + evaluation.json）才给下载，别的一律拒绝。服务器不提供"顺手翻目录"的可能。

## 闯关题（先自己答，答案在最底下）

1. 你用种子 7 生成了一次，然后想找回第一次（默认种子 20260927）的那批数据——需要留过档才行吗？重造出来的和第一次会一字不差吗？为什么？
2. 注水日报 12,410 行，不许看 manifest，用井数和天数把 12,410 算出来。
3. 实验 2 的限流，如果不做（允许同时跑多个生成），在最坏情况下服务器会发生什么？

---
---

**闯关答案（做完题再看）**

1. 不需要留档，重造就行。本次用的种子记在 manifest 里（seed 字段，默认 20260927），用 `"seed": 20260927` 重发一次，出来的一字不差（实验 3 已证：同种子两次生成的文件指纹完全相同）。这套数据永远可以"从种子复现"。
2. 34 口注水井 × 365 天 = 12,410。井数来自 well_info（120 = 86 EW + 34 IW），天数来自配方里"从哪天开始、造多少天"那两行。
3. 一次生成要算 67 万行，会吃掉大半 CPU 和内存；同时来 N 个，内存不够时机器只能拿硬盘硬撑、慢到像死机，严重时运行中的程序会被系统强制关掉，服务器上其他程序（比如正在查数据的人）也会被拖死。所以宁可拒绝（429），也不让它垮。
